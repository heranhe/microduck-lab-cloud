## 1. 结论摘要

根本问题不在视觉样式，而在**产品里没有"一次训练（Run）"这个统一对象**。同一次训练的进度、停止按钮、检查点、地面上的鸭子、产出的 ONNX 分散在四个面板和多个目录里，彼此没有关联。

| # | 核心问题 | 严重度 |
|---|---|---|
| 1 | 没有常驻的训练进度；右上状态条只有计时，没有步数/百分比/剩余时间 | 高 |
| 2 | 后端支持同目录续训，但 UI 没有"继续训练"入口；停止后只能微调（新目录、步数清零）或从头重训 | 高 |
| 3 | Colab 点停止会直接释放运行时，远端已保存的中间检查点随之丢失 | 高 |
| 4 | 训练刚开始时地面上的学员鸭子挂的是零策略，第一次快照要等约 15 万步；场景里也没有标记区分"学员"与"旧策略" | 中 |
| 5 | 本地与云端是两套完全不同的训练程序，云端只有 2 个任务，动作被迫和算力绑定 | 高 |
| 6 | ONNX 散落在多处；下载接口找不到 `policy.onnx` 时会退回下载 `live.onnx`，文件名却相同 | 中 |
| 7 | 各面板职责重叠：停止按钮两处、进度信息两处且都不完整，"策略"一词重复出现 | 中 |

## 2. 现状：界面各区域在做什么

| 区域 | 实际作用 | 主要文件 |
|---|---|---|
| 左上"鸭子实验室"（HUD） | 场景里每只鸭子的实时数据：策略名、实际/目标速度（m/s）、回合时长 t、跌倒次数、平均奖励 r̄；底部 CPU / 内存条；连接状态"在线" | `components/Hud.tsx` |
| 右上 训练 / 云算力 / 策略 三个按钮 + 状态条 | 三个面板的入口；状态条显示"算力来源 · 设备 · 动作 + 计时"和"停止 / 断开"按钮 | `components/CloudPanel.tsx` |
| 右侧"策略"面板 | 策略库：官方发布（Pollen）/ 我们的运行 / 检查点；可拖到鸭子上分配，或拖到空地生成新鸭子 | `components/PolicyPanel.tsx` |

## 3. 发现的问题

### 3.1 没有常驻训练进度

- 右上状态条（`CloudPanel.tsx` 的 `statusBar`）只显示 `device`（如"本机 · CPU · 单脚站立"）和计时器，**没有步数、百分比、预计剩余时间、下次快照时间**。
- 完整进度（"训练中… 已完成 49,152 / 4,000,000 步"、奖励曲线）只在训练面板的卡片里（`TeachPanel.tsx` 的 `statusLine`）。面板收起或滚动后就看不到。
- 卡片里的进度条很细，深蓝色在深色背景下几乎不可见；49k/4M 时只填充几个像素。
- 停止按钮有两处：状态条一个，训练卡片一个（`TeachPanel.tsx` 中"stop training"）。进度信息也有两份，但都不完整。

### 3.2 检查点与续训：后端已支持，UI 没接上

**后端已有的能力**（`microduck_local/src/microduck_local/train_behavior.py`）：

- 每 `SNAP_STEPS = 150_000` 步原子覆盖写入 `model.zip`、`vecnormalize.pkl`、`live.onnx`。
- 传 `--init-from <本 run 自己的目录>` 即为**真正的续训**：步数计数接着累计、学习率调度接着走、`progress.jsonl` 接着追加，`--steps` 保持为绝对目标。（文件头部注释有详细说明。）
- `viz_server.py` 的 `TrainingJob.scale()` 已经在用这条逻辑做"杀掉再热重启"。

**UI 上的缺口**：

- 结束后的卡片只有两个按钮（`TeachPanel.tsx`）：
  - "按调整后的配方重新训练"：从零开始。
  - "微调当前结果"：`initFrom` 指向**另一个**新目录，步数清零，重新给一份完整预算——**不是续训**。
- 停止后的状态文案是"训练已停止，小鸭子保留最近的快照"，没有"继续训练"按钮。
- 因此"中断后再开始"没有任何界面可操作。

**"没训练完的结果有没有用"**：

- 用于继续训练：有用。最多丢失最近一次快照之后的进度（约 15 万步；按截图速度约 4 分钟一次）。
- 用于部署/当成品：**不一定**。强化学习中途策略质量并不单调上升。代码里明确记录了一次失败的尝试——自动挑"最佳检查点"结果反而更差（`train_behavior.py` 中 `_on_rollout_end` 的注释：最终策略在三个 run 上都优于"最佳"检查点）。所以中途检查点必须先评估（跌倒率、实际达到速度、存活时长），不能按步数默认可用。
- 教动作流程默认 `checkpoint_every=0`，**只保留最新一份**，没有历史版本。策略面板里的 `cpu-walk-…@500k` 那类带 `@` 的检查点来自另一个独立的行走训练脚本，不是训练面板启动的任务。

### 3.3 停止的语义：本地是"直接杀"，Colab 是"直接释放"

**本地**：`TrainingJob.stop()` 调用 `_terminate_tree(wait_s=0)` 后直接置 `status = "stopped"`，不等训练脚本收尾。训练脚本里其实有干净的停止路径（`_stop` 标志 → 最终快照 → 导出 ONNX → 写 "done" 行，plateau 早停就走这条），但用户点停止时没有使用它。

**Colab**（`colab_jobs.py`）：

- `stop()` 设置 `cancel_requested`，工作线程立即返回，随后 `_release()` 执行 `colab stop`。
- 只有状态为 `done` / `failed` 时才会下载 `policy.onnx`、`checkpoint.pt`、日志。
- 远端脚本用 `--agent.save_interval` 保存的 `model_*.pt` 位于 `/content/...`，运行时一释放就丢失。
- 远端只回报 `setup / training / exporting / done / failed`，**没有迭代数或奖励**，所以本地只能显示计时。
- 轮询连续失败 6 次（`MAX_POLL_FAILURES`）会直接放弃并释放，同样不取回检查点。
- 实验室重启后，进行中的任务被标为 `detached`，提示"check and stop this Colab session"，同样没有取回检查点的路径。

### 3.4 场景里看不到"它在学"

- 训练启动时，`start_local_training()` 创建 `trainee` 鸭子并挂**零策略**，标签为"🎓 … (untrained)"；`live.onnx` 要等第一次快照才出现。
- 第一次快照在 15 万步后。截图时才 4.9 万步，所以地面上没有动作。
- 截图里地面上那只叫 `cpu-walk-20260908-1659@500k` 的鸭子是旧策略，与当前训练无关。场景里没有任何标记区分"本次训练的学员"和"别的策略"。

### 3.5 面板职责重叠、命名混乱

- "策略"一词同时是顶部按钮、面板标题、HUD 的列名。
- 策略面板的三个分组（官方 / 我们的运行 / 检查点）把"来源"和"粒度"混在同一层。
- 训练面板同时承担"启动向导 + 实时监控 + 结果处理"三件事。
- 内部 ID（`cpu-walk-20260908-1659`）直接作为显示名。

### 3.7 ONNX 散落，且下载存在"拿错文件"的坑

## 4. 目标设计：以"一次训练（Run）"为中心

### 4.1 四个层次

1. **任务（Job）**：正在运行的训练，全局唯一，常驻显示。
2. **运行（Run）**：训练结束或中断后留下的目录，有状态（进行中 / 完成 / 已中断 / 失败）。
3. **检查点（Checkpoint）**：Run 里的时间切片，带评估数据。
4. **场景（Scene）**：观察检查点的地方；每只鸭子都标明"挂的是哪个 Run 的哪个检查点"。

### 4.2 状态机

```
空闲 → 准备中（分配算力/启动环境）→ 训练中 ⇄ 暂停中（已存检查点）
                                    ↓           ↓
                                  完成       已中断（可续训）
                                    ↓           ↓
                                    └→ 评估 → 发布 / 微调 / 续训
失败 → 查看日志 / 从最近检查点续训
```

**规则：**

- "停止"一律改为"**保存并停止**"：先写检查点，再结束进程或释放云资源。
- 另设"强制终止"（红色、二次确认），仅用于卡死。

### 4.3 布局

```
┌──────────────────────────────────────────────────────────────────┐
│ [A] 训练任务条（顶部/左上，常驻）                                   │
│ 🦩 单脚站立 · 本机 CPU · ▓▓░░░░ 1.2%  49k/4M · 615步/s · 剩余≈1h48m │
│ 下次快照 @150k（≈2分钟）· 最近检查点：无   [⏸ 保存并暂停] [⋯]       │
├───────────────┬──────────────────────────────────┬───────────────┤
│ [B] 场景观察  │                                  │ [D] 策略库     │
│ 场景里的鸭子  │         3D 场景                   │ 按 Run 分组：  │
│ 🎓 学员(本次) │  学员鸭子头顶显示：               │ ▸ 单脚站立 #3  │
│   @0 未训练   │  "🎓 学员 · 快照 @0 · 未训练"     │   ● 进行中     │
│ cpu-walk@500k │                                  │   @150k @300k… │
│ 速度/跌倒/r̄   │                                  │ ▸ cpu-walk     │
├───────────────┘                                  │   ■ 已中断     │
│                                                  │   [▶ 续训]     │
│                                  ┌───────────────┴───────────────┐
│                                  │ [C] 训练工作台（可折叠）        │
│                                  │ 标签页：新建 | 监控 | 结果      │
└──────────────────────────────────┴───────────────────────────────┘
  快捷键说明 → 收成右下角 "?" 按钮
```

### 4.4 各区域职责

**A. 训练任务条（最重要，替代现有右上状态条）**

- 训练时**始终可见**，不随面板开关消失。
- 内容：动作名、算力、进度条与百分比、当前/总步数、速度（步/秒）、预计剩余时间、下次快照倒计时、最近检查点、当前阶段（课程训练时）。
- 按钮只保留这一处："保存并暂停"，以及"⋯"菜单（强制终止、打开日志、跳到监控页）。**训练卡片里的停止按钮删除**。
- 云端任务额外显示 GPU/机型和费用速率；远端尚无进度时明确写"云端进度暂不可用，已运行 12 分钟"。
- 空闲时收成小胶囊："无训练任务 · 新建训练"。

**B. 场景观察（现左上 HUD，降为次要）**

- 标题改为"场景里的鸭子"，明确是观察面板。
- 每行新增两个字段：**来源 Run**、**检查点步数**。学员鸭子置顶并带 🎓 标记。
- 点击某行，在策略库里高亮对应 Run 与检查点，两个面板联动。

**C. 训练工作台（现训练面板拆为三个标签页）**

- **新建**：选机器人 → 选动作 → 选算力 → 预算与检查点间隔 → 开始。
- **监控**：奖励曲线、各奖励项、并行环境数。任务条点一下跳转到此。
- **结果**：Run 结束或中断后显示，按状态给出主操作：
  - 已中断："▶ 从 @450k 继续训练"（同目录续训，步数接着累计）。
  - 已完成："评估"、"微调"（新目录、保留权重、步数清零）、"重新训练"（从零）。
  - 每个按钮旁写清后果，如"继续：步数接着 450k 往后计"。

**D. 策略库（重构右侧策略面板）**

- 两级结构：第一级是来源（官方发布 / 我的 Run），第二级是每个 Run 下的检查点时间线。
- 每个 Run 显示状态徽章（● 进行中 / ✔ 完成 / ■ 已中断 / ✗ 失败）、算力来源（本机 / Colab / HF）、格式（SB3 / mjlab）。
- 每个检查点显示评估摘要，如"跌倒 12% · 0.08 m/s · 存活 9.2 秒"；未评估则显示"未评估 [评估]"。
- 菜单：放入场景、与当前学员对比、从这里续训、导出 ONNX、发布、删除。
- 格式不兼容（如 Colab 的 `.pt` 无法在本地续训）时，"续训"置灰并说明原因。
- 显示名称用"行走 · 本机 · 9月8日 16:59"，内部 ID 放悬停提示。

### 4.5 让用户"训练一开始就在地面上看到动作"

1. 训练启动时把学员鸭子**自动放到场景中央并选中**，镜头对准。
2. 头顶标签："🎓 学员 · 快照 @0（未训练）· 下次更新 @150k"，让用户知道此刻不动是正常的。
3. **缩短前期快照间隔**：前 30 万步每 5 万步一次，之后恢复 15 万步，让用户在约 1 分钟内看到第一次变化。（注意：快照包含 ONNX 导出与 `model.zip` 写入，需实测频率对吞吐的影响，见第 9 节。）
4. 每次热加载新快照给出提示："🎓 学员已更新到 @300k"，并在奖励曲线上打点。
5. 可选：学员旁放一只挂"上一个快照"的半透明鸭子，便于看出进步。

## 5. 训练结果与 ONNX 的存放

### 5.1 现状

| 位置 | 内容 | 问题 |
|---|---|---|
| `microduck_local/runs/<run>/live.onnx` | 训练中每 15 万步覆盖的预览快照 | 只该用于看训练过程，却会被当成结果下载 |
| `microduck_local/runs/<run>/policy.onnx` | 训练正常结束后导出的最终策略 | 中断的 run 没有这个文件 |
| `microduck_local/runs/<run>/checkpoints/` | 只有 `model_*.zip`、`vecnormalize_*.pkl` | 没有 ONNX，也没有评估结果 |
| `microduck_local/runs/colab/<随机id>/` | Colab 的 `policy.onnx`、`checkpoint.pt`、`job.json` | 目录结构与本地 run 不同；现有 3 个任务目录里只有 `job.json`，没有取回任何结果 |
| `microduck/policies/*.onnx` | Pollen 官方 9 个策略 | 上游仓库克隆，只读 |

**具体的坑**：`GET /runs/{name}/policy.onnx`（`viz_server.py` 中 `download_policy`）依次尝试 `policy.onnx`、`live.onnx`，下载文件名统一为 `{name}.onnx`。所以下载一个没训练完的 run，拿到的是中途快照，文件名却与成品一模一样。

**不要往 `microduck/policies/` 里放自己的文件**：那是上游仓库，且 `xtask` 中有校验——该目录下每个 `.onnx` 必须在所有打包位置被打包，多放一个会让打包检查失败。

### 5.2 建议：三层结构

**第一层：训练工作区（每次训练一个目录，本地和云端统一）**

```
microduck_local/runs/<run_id>/
  run.json          动作、机器人、算力来源(本机/Colab/HF)、格式(SB3/mjlab)、
                    配方版本(代码哈希+权重+动作片段)、总预算、状态
  progress.jsonl    训练曲线
  train.log
  live.onnx         仅供场景预览；不参与下载或发布
  checkpoints/
    000450000/      model.zip  vecnormalize.pkl  policy.onnx  eval.json
    000900000/      ...
  final/            model.zip  vecnormalize.pkl  policy.onnx  eval.json   （正常完成才有）
```

- 每个检查点同时导出 ONNX，并跑一次评估，写入 `eval.json`（跌倒率、达到的速度、存活时长）。
- Colab / HF 结果按同一结构放入 `runs/<run_id>/`，用 `run.json` 的来源字段区分，取消单独的 `runs/colab/<随机id>`。
- 下载接口**不再**回退到 `live.onnx`；没有正式产物时明确返回"该 run 尚无可下载的策略，可下载 @xxx 检查点"。

**第二层：我的策略库（只放确认过的结果）**

```
microduck_local/library/<机器人>/<槽位>/<名字>.onnx
microduck_local/library/manifest.json
```

- 槽位对应真机 `robotd.toml` 的 `[policy]`：`walk / stand / sitstand / ground_pick / kick_left / kick_right`；自定义动作（如"单脚站立"）放 `custom`。
- `manifest.json` 每条记录：来源 run 与检查点步数、sha256、输入输出维度、评估数据、发布时间。
- **发布前校验接口**：必须是 61 维输入、14 维输出。`robotd` 加载时同样检查，维度不符会直接拒绝加载（`deploy/robotd.toml` 注释："All must be 61-input, 14-output"），提前在电脑上拦住。

**第三层：部署到真机**

- 从策略库选策略与槽位，推送到机器人；在机器人 `robotd.toml` 的 `[policy]` 中把对应槽位指向该文件（该配置本就支持："Point one at your own .onnx to try a build without cutting a release"），重启 `robotd`。
- 记录上一次配置，支持一键回滚到官方策略。

### 5.3 UI 上的结果呈现

训练结束/中断后，训练工作台切到"结果"页，按顺序：

1. **摘要**：状态、训练步数、用时、算力来源。
2. **评估卡**：最终策略/最近检查点的跌倒率、速度、存活时长，**与官方基线对比**（如单脚站立对比 `alpha_stand`）。没有基线对比就无法判断结果能不能用。
3. **检查点时间线**：每个点带评估分数，可挑分数最高者，不一定是最后一个。
4. **操作**：放入场景对比 → 发布到策略库（选槽位）→ 下载 ONNX → 部署到机器人 → 继续训练 / 微调 / 重新训练。

策略面板同步改为三组：**官方**（只读）/ **我的发布**（可直接上真机）/ **训练记录**（所有 run 与检查点）。

## 6. 算力来源与动作解耦

### 6.1 为什么有的动作只能本地

本地和云端跑的是**两套不同的训练程序**：

| | 本地 | 云端（Colab 与 HF 共用 `_remote_runner`） |
|---|---|---|
| 程序 | 本仓库 `microduck_local`：CPU 版 MuJoCo + Stable Baselines 3 PPO | Pollen 官方 `microduck_rl`（克隆固定版本，用 `mjlab` 跑） |
| 动作定义 | `behaviors/` 下的 Python 配方（奖励项、出生姿态、终止条件、课程阶段） | 官方已注册的任务名 |
| 可用动作 | 全部教学动作 + G1 + MARS | 白名单 `TASKS` 仅两个：`Mjlab-Velocity-Flat-MicroDuck`、`Mjlab-VelStand-Flat-MicroDuck` |
| 产物 | `model.zip`、`policy.onnx` | `checkpoint.pt`、`policy.onnx` |

云端机器上没有 `microduck_local` 的任何代码，所以配方、调过的权重、动作片段都不存在。

前端用一张写死的映射表把两边凑在一起（`duck-viewer/lib/cloudCompute.ts`）：

```ts
export function cloudTaskFor(robotId: string, behaviorId?: string): string | null {
  if (robotId !== "microduck") return null;
  if (behaviorId === "stand") return "Mjlab-VelStand-Flat-MicroDuck";
  if (behaviorId === "official_velocity") return "Mjlab-Velocity-Flat-MicroDuck";
  return null;
}
```

后果：

- 只有两个动作能上云；G1、MARS 全部不能。
- 连"保持站立"映射过去也**不是同一个任务**。`TeachPanel.tsx` 里有提示："云端使用官方 VelStand 任务（行走＋跌倒恢复），与本机'保持站立'配方不同"。用户以为在云端训练站立，实际训练的是另一个任务。
- 两边产物格式不同，**本地与云端不能互相续训**。
- `VelStand` 任务还要求预先准备两个教师检查点（`colab_jobs.py` 的 `TEACHERS`），缺失时不分配 GPU。

### 6.2 优化方案

目标：**"训练什么"和"用什么算力"是两个互不相关的选择。**

**第一步（推荐先做）：云端跑同一套本地训练程序**

- 远端脚本不再克隆上游去跑 `mjlab`。改为把**当前这份** `microduck_local` 打包上传（代码、`behaviors/`、动作片段、本次权重配置），远端执行与本地相同的命令：`train-behavior <动作> --weights-json … --envs N`。
- 收益：
  - 所有动作（含 G1、MARS）都可上云。
  - 产物与本地一致，直接落入统一的 `runs/<run_id>/`。
  - **跨机器续训打通**：本地训到一半可挪到云端继续，反之亦然。
  - 远端进度直接读 `progress.jsonl`，任务条与本地显示一致。
  - 可同步解决 3.3 中"云端无进度、停止丢检查点"。
- **代价**：该训练程序主要吃 **CPU**，GPU 几乎用不上。Colab 免费版只有约 2 个 vCPU，可能比本机 Mac 更慢。所以上云的价值是"不占用本机、可合盖、可并行多个任务"，不是"更快"。算力选项应按 CPU 核数推荐（如 HF 的多核 CPU 机型），而不是一律推荐 T4/A100。

**第二步（长期）：为需要速度的动作接 GPU 引擎**

- 官方 `mjlab` + MuJoCo Warp 可在 GPU 上并行数千环境，才是真正快几十倍的方案，但每个动作需在 `mjlab` 中重写奖励。
- 做法：把配方抽象成**与引擎无关的描述**（奖励项、权重、出生姿态、终止条件、课程阶段），分别写 CPU 引擎与 GPU 引擎两个适配器。两边已共用同一机器人模型与 61 维观测接口，差异主要在奖励写法。
- 适配好的动作多一个"GPU 加速"选项；未适配的动作仍可在云端用 CPU 引擎跑，**不会被挡住**。

### 6.3 用户界面上的表现

1. **选动作**：只关心训练什么，界面上不出现任何云端限制。
2. **选算力**：本机 / Colab / HF 全部可选。每个选项显示：
   - 预计用时与费用（按该动作步数预算与机型速度估算）；
   - 训练引擎（"CPU 引擎"或"GPU 加速（官方引擎）"）；
   - 是否支持暂停与续训；
   - 一句推荐（例："该动作在 Colab 免费版预计比本机慢约 2 倍，推荐 HF 8 核 CPU"）——只提醒，不禁止。
3. **引擎自动选择**：该动作有 GPU 适配且选了 GPU 机器就用 GPU 引擎，否则用 CPU 引擎。用户无需理解"接入云端"。
4. **可复现**：`run.json` 记录配方版本（代码哈希、权重、动作片段），保证云端训练的就是面板上所见的配方。
5. **官方 VelStand 单列**为"官方行走＋站立（VelStand）"，不再冒充本地"保持站立"。

## 9. 需要先验证的假设与风险

1. **快照频率对吞吐的影响**：每次快照包含 ONNX 导出与 `model.zip` 写入。把前期间隔缩短到 5 万步前，需实测对步/秒的影响。
2. **"保存并停止"的收尾耗时**：SIGTERM 后训练脚本需要走完快照与 ONNX 导出；多进程环境下要确认不会遗留 worker（`_sweep_workers` 已有相关处理，需回归验证）。
3. **云端跑 `train-behavior` 的依赖**：需确认 `microduck_local` 的依赖（`uv sync`）在 Colab/HF 镜像上可安装，且上游 MJCF 模型（`microduck_rl`）在远端可用。
4. **CPU 引擎在云端的实际速度**：Colab 免费版 vCPU 很少，需要先实测再决定推荐策略。
5. **评估的定义**：跌倒率、达到的速度、存活时长的判定标准需和各动作的目标对应（如单脚站立看的是站立时长而非速度），评估指标应随动作配置。
6. **评估成本**：每个检查点都评估会占用算力；可只对用户选中的检查点评估，或后台低优先级评估。
7. **真机部署的安全性**：推送到真机前建议强制"在仿真中通过基线对比"这一步，并保留回滚。
8. **本文基于代码阅读**：未实际运行训练、未做性能测量；第 4.5、7 节中涉及数值（快照间隔、检查点间隔、超时）的均为建议起点，需要实测调整。
